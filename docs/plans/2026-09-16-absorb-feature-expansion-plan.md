## 3. 使用者與成功定義

### 3.1 一般使用者

打開產業圖，能理解公司在做什麼、與其他公司有何關係；選幾家比較後加入關注，隔天知道有什麼新事實。

### 3.2 深入研究者

能展開每一項結論的來源、資料日期、適用範圍與相反證據；能分辨已確認關係、歷史關係和只有題材重疊的公司。

### 3.3 第一版成功的具體樣子

1. 新訪客不必註冊，即可完成「產業圖 → 公司關係證據 → 同業比較」。
2. 登入後加入關注，Web 與 LINE 讀回同一筆狀態。
3. 回到我的關注，能分清「有新事件」「沒有新事件」「資料未更新」。
4. 查看 KOL 觀點時，能回到原始來源，知道紀錄是否完整與成效如何計算。
5. ASKsorb 的回答可回查到相同紀錄，不憑空補足缺漏。

這些是驗收目標；使用成長與留存屬上線後觀察，不預先保證。

## 5. A：產業關係圖與同業比較

### 5.1 第一版內容邊界

以 AI 伺服器題材整理運算晶片、製造／封裝、記憶體、伺服器組裝、電源、散熱及連接等環節。公司可屬多個環節，不能強迫歸入單一類別。

研究蒐集目標為約 20～30 家公司；這是工作量上限估計，不是必須湊足的驗收數量。只發布證據足夠的公司與關係，另列已檢視但缺乏證據的範圍。資料不足時縮小並如實標示覆蓋，不補假資料。

外國客戶或非上市企業可作為關係節點，標記市場與身分類型；沒有可驗證行情時只顯示關係，不提供價格或納入比較。

### 5.2 關係分類與畫法

| 關係 | 定義 | 呈現規則 |
|---|---|---|
| 供應關係 | 有來源明示 A 提供產品／服務給 B | 箭頭 A → B，附產品範圍與來源 |
| 合作關係 | 有雙方或官方公告支持合作 | 無方向連線，說明合作內容 |
| 競爭關係 | 在明確產品／市場有可核對的競爭依據 | 無方向連線，不能只因產業相同就建立 |
| 同一環節／題材 | 公司業務屬於相同研究分類 | 以分組框或標籤呈現，不畫成交易關係 |

「供應商」與「客戶」是同一條有方向關係的兩端，不重複建兩筆相反紀錄。

來源可信度與關係狀態分開：來源可為公司揭露或具名二手報導；狀態為有效、歷史、待確認。預設圖只呈現經審核且未過期的公司／官方明示關係。二手報導及爭議放在細節中，不冒充已確認連線。

不提供「供應機率 85%」這類沒有校準依據的分數，也不把股價相關性標成商業關係。

### 5.3 使用流程

1. 進入題材頁，先看到各環節與涵蓋範圍。
2. 搜尋或點選公司，圖上只顯示該公司及直接關係，預設不展開兩層。
3. 點選連線，在面板讀到「誰與誰、什麼產品、何時揭露、證據在哪裡」。
4. 點另一家公司，可切換研究中心；麵包屑與返回按鈕保留前一個中心。
5. 公司面板提供「查看個股」「加入比較」「加入關注」。

單一中心預設最多顯示 12 個關係節點，超出時明示總數並提供展開／列表，不能悄悄隱藏成資料不存在。節點位置採固定環節布局，第一版不做力導向動畫或自由編輯。

### 5.4 證據面板

必填：關係描述、產品／業務範圍、來源標題、來源發布日、來源 URL、頁碼或段落定位、最近審核日。

可選：關係開始／結束日、客戶營收占比。沒有揭露就顯示「未揭露」，不以公司整體營收代替。

產品政策：有效關係每 90 日進入複核名單；逾期標為待複核並退出預設有效圖，不推論合作已終止。每週檢視新增公告與來源失效；更新來源不得抹去舊版依據。

### 5.5 同業比較

第一版預設只比較同市場的 2～4 家台股，使用者可自行換股；屬於不同環節時顯示差異，避免暗示業務等同。

必做欄位：公司、環節、資料日、價格幣別、5 日及 20 日價格變動、MA20 狀態、量比、既有可用籌碼指標、已確認關係與資料覆蓋。

價格變動僅在窗口和公司行動處理可核對時顯示；不足的項目保留缺值。比較行情的共同基準日採所選公司可驗證的共同交易日，超出既有新鮮度門檻就不做最新排名，原始日期保持可見。

財務比較是 B 的資料驗收通過後補入同一頁：月營收年增、同期間毛利率／營業利益率、TTM EPS。本益比另依可核對 EPS、幣別、股本／每股口徑計算；負 EPS 顯示「不適用」，不產生負值便宜排名。年累計與單季、合併與個別報表不得混排。

第一版不做「AI 綜合最佳股」分數，不將缺值轉零，也不給跨產業總冠軍。

### 5.6 A 驗收

- 任一預設可見連線都有可開啟、能定位的支持來源，方向與文字一致。
- 人工抽查各關係類型，分類同儕不會被自動轉成供應鏈。
- 未登入可使用圖、列表與比較；加入關注才進入既有登入流程。
- 390px 手機可完成點公司、看證據、加比較，不依賴 hover 或拖曳。
- 過期來源、未知代碼、資料缺失、重複公司及超過 4 家比較都有明確行為。

## 6. B：今日變化、事件時間軸與行事曆

### 6.1 我的關注如何改變

頁面順序：資料更新狀態 → 有新變化的公司 → 接下來已公布事件 → 全部關注公司。

每日變化顯示兩類資料，視覺上清楚分開：

- 公司事實：營收／財報發布、法說、除息公告、重大訊息、已確認關係異動。
- 市場觀察：既有系統提供的量能、價格、交易狀態等變化，說明比較日期。

第一版「今日」定義為最近已完成市場交易日及其對應發布窗口，頁面以實際日期作標題。台灣與美國不能共用台北日曆日判定新鮮度。

沒有新紀錄可顯示「這個觀察窗口沒有新增事件」；來源抓取失敗或關注公司未涵蓋時顯示「事件資料尚未更新／未涵蓋」，兩者不可互換。

### 6.2 事件卡與時間軸

每張卡有：公司、事件類型、標題、兩行事實摘要、來源發布時間、事件生效時間、資料期間、官方來源，以及更正狀態。

同一件公告使用來源識別碼去重；更正公告與原公告建立關聯並保留版本。新加入關注不代表公司過去事件都是今天新增。

排序先區分已公布的未來事件與已發生事件，區塊內依日期；不使用沒有依據的利多／利空評分。重大訊息僅表示公告類別，不表示預期價格方向。

### 6.3 行事曆

第一版包含法說、財報公布、月營收公布、除息等取得明確日期的事件。歷史公布紀錄可進時間軸；只有已公布日期才能放入未來行事曆。

未公告的財報日期不依去年日期推成今年確定日；只有日期而無時間時顯示「時間未公布」。取消、延期、日期更正保留歷史。

預設為未來 14 日與過去 30 日列表，另可切月曆；桌面與手機都可切公司和事件類型。登入後可選「只看我的關注」，匿名模式顯示本版涵蓋公司。

### 6.4 通知邊界

第一版完成站內摘要與既有關注整合，不自動新增 LINE 推播訂閱，也不變更現有提醒規則。

每日 LINE 摘要列為後續可選項：使用者主動開啟、每日最多一則、無新事件不發、可關閉，且發布失敗不反覆補發。要啟用時先檢查現有配額與費用；本次計畫不承諾免費推播。

### 6.5 B 驗收

- Web／LINE 清單沒有分叉，加入與移除後重新載入結果一致。
- 同一公告重跑匯入不產生重複卡片；更正保留前後關係。
- 來源中斷、跨日、週末與公司停牌不產生虛構的「今日變化」。
- 使用者 A 不能透過 URL 或請求參數讀取使用者 B 的清單。
- 財務比較每個數值可回到對應報表期間；不同口徑不強制排名。

## 7. C：KOL 觀點與成效追蹤

### 7.1 產品定位與初始範圍

頁面名稱為「觀點追蹤」，提供「明確推薦」篩選；保留使用者想找推薦選股的入口，同時避免把所有提及都歸類為推薦。

研究候選名單目標為 3～5 位以台股為主、公開內容可穩定回查的創作者。若使用者指定名單優先評估；未指定時依可取得性、原始時間、具體標的與持續公開更新選擇，並在實作交付中附入選理由。

版本 1.1 以第 7.6 節三個指定 X 帳號作為新增優先名單，取代「僅台股創作者」的初始限制。既有 YouTube 紀錄需重新確認來源與審核狀態，不因已放入 JSON 就算已確認內容。

不以名氣、歷史漲幅或預想績效決定是否收錄。第一版可先做公開文章及具時間點的影片人工紀錄，不依賴大量付費轉錄。

### 7.2 紀錄內容

| 欄位 | 規則 |
|---|---|
| 創作者 | 穩定 ID、公開名稱、官方頻道／網站；不假裝本人認證 |
| 來源 | 原始 URL、標題、影片時間點或文章段落；來源失效可辨識 |
| 時間 | 原始發布時間、首次取得時間、人工確認時間分開儲存 |
| 標的 | 明確公司／證券 ID；綽號不明時不強配股票 |
| 立場 | 提及／看多／看空／明確推薦／有條件觀點／不明確 |
| 理由 | 簡短摘要與支持原文的定位，不存整篇付費內容 |
| 期限與條件 | 原作者有說才填；未說就是未說 |
| 後續 | 延續、轉向、撤回、條件失效或更正，連回原紀錄 |
| 審核 | 待審／已確認／有爭議／來源失效，及修訂歷史 |

一句話提到數家公司，只有明確可歸因的立場才拆成各公司紀錄。多位創作者轉述同一新聞，不能顯示成數個獨立研究來源。

### 7.3 頁面流程

1. 觀點首頁依發布日顯示，篩選公司、創作者、立場和日期。
2. 點開紀錄，讀理由、原始定位、條件及後續變化。
3. 創作者頁標明涵蓋平台、收錄起日、漏收區間及審核狀態。
4. 個股頁反查誰提過、意見分歧在哪裡，與公司官方事件分區呈現。

不做人氣買進榜、粉絲留言板、付費跟單或自動交易。第一版不製作跨 KOL 成效排行榜。

### 7.4 成效計算契約

名稱使用「觀點發布後價格觀察」，不宣稱是創作者真實持倉績效。

1. 第一版只對明確、無附帶觸發條件、經人工確認的方向性觀點計算。單純提及及有條件觀點仍可展示，成效標示不納入，並說明原因。
2. 基準取原始發布時間之後，下一個完整交易日的收盤價；例如週五盤中發布，取後續下一個完整交易日的收盤，不取發布前價格。實際日期顯示給使用者。
3. 只有發布日而沒有時刻時，保守取其後下一個完整交易日，標明時間精度；日期或時區不明則不計算。
4. 以基準日為第 0 日，觀察其後第 5、20、60 個市場交易日收盤。到期日依官方市場行事曆決定，不能跳過停牌日把持有期偷偷延長。
5. 顯示價格變動 `(P_h / P_0 - 1) × 100%`。公司行動處理與價格來源版本必須可核對，否則該區間不發布結果。
6. 第一版採拆股調整、未含現金股息的價格報酬；基準指數使用相同「價格報酬」口徑。若現有來源只能提供混含股息且無法分離的調整價，該結果暫不發布，不能混算。
7. 台股先以 TAIEX 價格指數作共同參照；頁面說明它不能代表每檔股票的風險與產業曝險。相對報酬以同起迄日的兩者報酬相減，單位是百分點。
8. 期間最大回撤以逐日收盤相對先前收盤峰值計算，標名「收盤最大回撤」。不足的逐日資料不推成盤中最大回撤，也不補成零。
9. 同創作者、同股票、同方向在既有 60 日觀察區間內的延續發言保留於時間軸，但不新增獨立成效樣本。轉向可建立新紀錄，第一版按紀錄展示，不將重疊樣本合成總績效。
10. 停牌、下市、來源失效、缺價、尚未到期都有獨立狀態；不從收錄總數中消失。更正不能挑選更漂亮的起算價。
11. 首次取得晚於發布的歷史紀錄標為回溯收錄，與持續追蹤的紀錄分開。歷史回填最多先研究 90 日，不聲稱已完整捕捉期間全部發言。
12. 看空紀錄呈現之後實際價格走勢，不把價格跌幅直接當成可實現放空收益；不估借券、槓桿及交易成本。

第一版展示樣本數、到期數、缺價數及每筆結果；不展示勝率排行榜，也不把樣本量門檻冒充統計可靠性。未來若做比較排名，需另訂完整收錄範圍、樣本重疊與選擇偏差處理規則。

### 7.5 C 驗收

- 每筆已確認觀點都有可定位來源；摘要忠實保留條件與否定語氣。
- 不明確標的、條件式推薦與單純提及不誤入成效樣本。
- 盤中、盤後、週末、時間不明、拆股、現金股息、停牌及下市案例符合上述契約。
- 負報酬與失效來源紀錄保留；未到期結果不顯示 0%。
- 樣本的收錄時間、修訂版本及價格來源可重現；回溯收錄有清楚標記。

### 7.7 來源取得、內容分類與跨市場識別

- 優先收錄可回查的原始貼文 permalink／post ID、發布時間與時區、貼文定位、簡短摘要、首次取得和人工審核時間。搜尋摘要只能作發現線索，不能單獨支撐已確認觀點。
- 每個帳號先檢視最近 30 日可取得內容，目標 5～10 筆可核對紀錄；不足時列出實際樣本與缺漏。來源不可讀時維持「待審／未涵蓋」，不編造摘錄。回溯收錄不假裝是當時即已追蹤。
- 第一版允許人工整理的版本化 JSON。自動化先驗證現有可用的合法取得途徑；需付費 API 或新增帳戶時交付具體成本與範圍後另行處理。網頁請求不即時抓 X。
- `content_type` 分為 `original_opinion`、`news_relay`、`flow_observation`、`trade_disclosure`；轉貼加上自己的分析時，可以拆出有原文支持的觀點，並保留原始消息關聯。
- `stance` 分為 `bullish`、`bearish`、`neutral`、`unclear`；中立必須是明確表態。`recommendation_kind` 另分 `explicit`、`conditional`、`mention`，不能把看多直接當買進推薦。人工確認前的自動抽取只算草稿。
- 否定句、假設、諷刺、引述他人、賣出期權和看空股票需分辨；`不建議買` 不可因包含「買」就分類為明確買進。
- 證券用 `market + symbol`，公司用 `company_id`。例如 `TW:2330` 與 `US:TSM` 可連至同一公司，但觀點數、行情、幣別及成效分開；未明示證券時保留公司層級，不硬配 ADR。
- 台美以外的公司先保留研究節點，標明市場；不把韓國數字代碼當台股。查不到主檔的代碼不提供行情／比較／成效。

來源正規化規則：

- X 原文只接受 `https://x.com/<handle>/status/<post_id>` 或可驗證等價的 `twitter.com` 貼文網址；正規化後保存 canonical URL、平台、immutable post ID、原始 URL、取得方式與查核時間。移除追蹤 query 和 fragment，拒絕非 HTTPS、帶 userinfo、非貼文路徑或只有個人首頁的網址。
- `source_id` 以平台與 immutable ID 組成，例如 `x:1234567890`；沒有 post ID 的截圖、搜尋摘要、轉述或無法回查的短網址只能保存為 `discovery_reference`／`pending_review`，不得進入有效觀點或成效樣本。
- 帳號首頁只用於 Creator 身分核對；個別觀點必須另有貼文 permalink。官方網站、影片與文章可作補充來源，但需標示 `source_kind`，不能把 Capafy 的彙整頁當成三個帳號的原始貼文。
- Capafy Alpha Consensus 只保存為 `reference` 來源（產品名稱、作者、頁面、查核時間、產品說明版本）；不把它的摘要、排名或更新頻率複製進 ABSORB catalog，也不在分母中新增虛構創作者。
- 若保存原文摘錄，限定必要短摘錄並附 `content_hash`、語言與授權／使用條件註記；無法確認再發布權利時只保存摘要、定位及連結。來源重導向須落在允許網域，服務端不接受任意 URL 形成內網請求。

每個來源可行性紀錄至少包含：`creator_id`、查核時間、canonical profile URL、核對名稱／頭像／簡介的結果、貼文 permalink 可用性、抽樣起迄、可核對筆數、取得方式、授權／條款備註、`last_success_at`、缺漏區間、狀態（`verified`／`partial`／`unavailable`／`pending_review`）與審核者。這份紀錄寫入 `docs/research/x-opinion-source-feasibility.md`，供 C1 及後續更新讀回；不以帳號名稱出現在 UI 當作來源已可用。

版本相容規則：

- `schema_version=2` 才能進入新的 consensus reader。v1 檔案可被唯讀載入以保留既有頁面，但缺少 `market`、`symbol`、`source_id`、`content_type`、`reviewed_at` 或時區欄位的紀錄要標 `legacy_unverified`／`pending_review`，不能在載入時默默補值或升級為已確認。
- 若需要遷移，先輸出新的複製檔並保留原始 v1、穩定 `opinion_id`、`outcome` 與版本雜湊；逐筆通過 validator 後才切換 reader。遷移失敗只讓該筆維持舊版可見與新狀態，不覆蓋有效 catalog。
- v2 新欄位的未知值、錯誤時區、重複 immutable ID、無法解析的證券主檔及來源失效，均產生可定位的 validation error；reader fail closed，不刪除原始紀錄來湊乾淨結果。

### 7.8 同股共識與分歧：計算契約

頁面分成「期間新增討論」與「截至時間的最新已收錄立場」。前者計算該窗口的活動，後者讓使用者看到較早表態並標明日期，避免把歷史內容當今天新增。

1. 預設窗口為近 24 小時、7 日、28 日，使用 UTC 做運算，畫面顯示時區及明確起迄；不足時不默默擴窗。使用者可自行擴窗，URL 保留選擇。
2. 只納入截止時間之前已取得、已審核且來源可用的紀錄；歷史重播也須滿足 `first_seen_at`、`reviewed_at` 不晚於截止時間，避免回溯資料洩漏。
3. 每位創作者、每項證券、每一比較期限只保留一個最新且未撤回的有效立場，沿用／反轉關係由紀錄 ID 連結。短期看空與長期看多分組呈現，期限不明者列「期限未提供」，不混算一致率。
4. 窗口內的看多、看空、中立、立場不明、有條件觀點分列；純新聞／資金流／他人交易另列。沒有提及、抓取失敗、未涵蓋是覆蓋狀態，不算中立票。
5. 首版以人數及理由為主，不顯示預測勝率。若展示多空比例，分母只含同期限、明確且無附帶條件的看多與看空帳號；分母為 0 顯示不適用，少於 2 個有效帳號標明不足以比較。
6. 同一消息被多個帳號轉述，用 `origin_group_id` 關聯；保留帳號活動數，同時顯示獨立來源群組數。各自有分析也只表示不同意見，不宣稱資訊獨立。
7. 每筆摘要附支持的 opinion IDs、理由及反對證據。最新紀錄撤回、互相矛盾但無法確認承接，或來源失效時，顯示待確認，不退回更早立場冒充最新。
8. 超出窗口的觀點放歷史脈絡，注明「最近已收錄」，不宣稱帳號目前仍持有。共識只描述收錄範圍，不等同全市場共識或預期報酬。

**驗算例（僅測試資料）：** A 看多、B 有條件看多、C 轉貼新聞、D 未涵蓋。顯示明確看多 1、有條件 1、新聞來源 1、未涵蓋 1；明確方向樣本僅 1，不呈現「三人看多」或 75% 共識。

查詢與狀態例：

- `GET /perspectives?market=US&symbol=NVDA&window=7&view=consensus&cutoff_at=2026-09-17T08:00:00Z` 回傳同一 `catalog_version` 下的共識、分歧、覆蓋狀態與 evidence IDs；頁面可再帶 `creator_id`、`stance`、`content_type` 篩選。
- `GET /perspectives/stocks/TW/2330?window=28&view=timeline` 只讀 `TW:2330`，不能因同公司有 `US:TSM` 就混入 ADR 觀點；無可用行情時仍回傳可核對觀點與 `price_status=unavailable`。
- 合法 query 的頁面回傳 200，但 payload／畫面必須明示 `ready`、`partial`、`stale`、`empty` 或 `unavailable`；空結果不代表來源完整。若沒有任何可讀 catalog，JSON／服務端契約可回 503 並附欄位化原因；有最後有效版本則回 200 `stale`，不得以空陣列覆蓋舊結果。
- 無效 market、symbol、creator、window 或無時區 `cutoff_at` 回傳 400 與 `field`／`reason`；未知 creator 不退回全帳號結果。頁面把 query 原樣保留在篩選與分享網址，ASKsorb 使用同一組參數。

### 7.9 立場時間軸、產業圖及頁面流程

- 觀點首頁沿用 `/perspectives`，提供市場／公司／創作者／立場／內容類型與時間窗口篩選，並切換「最新紀錄」「共識與分歧」。避免另增一組頂層導覽。
- 點公司開啟個股觀點詳情：帳號 × 立場摘要、各自理由、同意及分歧點、來源時間、取得狀態與時間軸。無行情時仍能查閱觀點，不生成空的價格圖。
- 時間軸保留首次論點、追加證據、延續、轉向、撤回及更正，以 `supersedes_id`／`continuation_of` 連結。延續發言不從時間軸刪除；第 7.4 節的成效樣本去重獨立處理。
- 創作者頁顯示官方帳號、涵蓋市場、最後成功取得／審核時間、缺漏區間、最新與歷史立場。完整性未知時明示抽樣收錄。
- 從觀點可跳到產業圖相關公司與關係證據；從關係證據也能反查相關公開論點。KOL 的供應鏈說法放「研究線索」區，只有另外取得官方支持來源並審核後，才能成為預設已確認連線。
- 390×844 手機用帳號卡片與垂直時間軸；1440×900 可用比較表。所有篩選、原文、時間軸與返回動作可用鍵盤，返回時保留 query。

### 7.10 更新與取得失敗

初版依可取得且已審核的批次更新。每個帳號分別顯示 `last_success_at`、`reviewed_through` 和缺漏，不能只放全站單一「已更新」。已成功查詢且零新貼文、抓取失敗、內容待審各有狀態；失敗保留最後有效版本並標日期，禁止發布空資料覆蓋舊版。刪文或失效來源保留紀錄 ID 與失效狀態，退出有效共識但不抹去歷史。

共識在有效 catalog 發布後重新計算，以 catalog_version 與 method_version 綁定；不另啟高頻模型呼叫。固定自動更新頻率待來源測試、成本與 runner 窗口核實後設定，這次計畫更新不建立排程。

## 8. D：ASKsorb 與功能整合

新增可回答的問題類型：

- 「這家公司有哪些已確認的客戶？資料是什麼時候的？」
- 「這兩家公司在產業鏈中的位置有什麼不同？」
- 「我的關注公司這個觀察日新增哪些公告？」
- 「這位 KOL 為什麼看好這家公司？後來有改變看法嗎？」
- 「Serenity 與 Michael 對這檔美股的理由有什麼不同？」
- 「最近 7 日哪些公司有多個獨立帳號表態？哪些只是轉貼新聞？」
- 「Unusual Whales 這筆是帳號立場、資金流資料，還是轉述他人交易？」

指定帳號必須解析至已驗證 creator_id；指定市場、公司、日期及截止時間套用第 7.8 節同一查詢。無法識別帳號就說明缺項，不回傳全部帳號冒充指定答案。回答中的共識人數、最新立場和來源須與相同 query 的頁面一致。

回答格式沿用結論在前、依據在後：簡短回答 → 來源連結與資料日 → 缺漏／相反證據 → 對應頁面入口。

公開問題讀取已審核的公開紀錄；個人關注問題經既有 session 取得身分。使用者在文字中聲稱自己是另一個 user ID 不產生授權。

先用結構化查詢回傳明確事實，沿用既有對話能力；不為此新增 RAG、向量資料庫或每次請求即時爬網。外部文章、影片文字與來源摘要都視為資料，不能執行其中的工具指令或改寫系統規則。

無來源時回答「目前沒有收錄足以確認的證據」，不能說「不存在關係」。KOL 意見與 ABSORB 的觀察分開，不把他人的目標價包裝成網站模型結論。

驗收包含：有資料、只有部分資料、來源過期、相反觀點、跨帳戶查詢與來源文字提示注入；既有問題回答不能退化成一律拒答。

## 9. 資料來源、模型與維護

### 9.1 來源可行性

| 資料 | 優先來源 | 第一版處理 | 已知限制 |
|---|---|---|---|
| 公司身分與市場行情 | 現有證券主檔、驗證後市場產物 | 沿用既有契約，不在網頁臨時抓行情 | 需重新確認歷史範圍、價格調整與日期語意 |
| 供應鏈與合作 | 年報、法說簡報、公司正式公告 | 人工整理與來源定位，版本化發布 | 商業關係不一定公開，不能承諾全市場完整圖 |
| 台股事件與財務 | TWSE／公開資訊觀測站；上櫃另驗證 TPEx 官方資料 | 先做來源與欄位驗證，再寫批次匯入 | API 存在不代表每個欄位、歷史與商業展示條件都已核實 |
| KOL 觀點 | 指定 X 帳號原始貼文、創作者公開原文、可核對影片片段 | 先核對帳號與原文，再人工建檔；批次取得須通過來源可行性驗證 | 公開可讀不代表已有可穩定匯入的 API；未取得資料顯示未涵蓋 |
| 美股財務與申報 | SEC EDGAR APIs | 列為美股擴充候選，不列第一版必做 | 標準 XBRL 仍需處理期間、單位與自訂欄位差異 |

官方參考：

- [TWSE OpenAPI](https://openapi.twse.com.tw/) 提供公開 API 目錄；實作前逐項驗證需要的端點、欄位、限制與樣本。
- [公開資訊觀測站](https://mops.twse.com.tw/mops/web/t120sb02_q10) 列有重大訊息、財務報告及月營收等入口；本輪只確認來源方向，未完成資料接入。
- [SEC EDGAR API 文件](https://www.sec.gov/search-filings/edgar-application-programming-interfaces) 說明公司申報與 XBRL JSON API，以及資料期間需要注意的差異。
- [YouTube captions.download](https://developers.google.com/youtube/v3/docs/captions/download) 明示下載字幕需具備影片編輯權限，不能把它當作任意 KOL 影片的通用字幕來源。

這些是來源調查，不是使用授權已完成的結論。第一版發布簡短整理、來源定位和連結；若某來源不能支持必要存取或展示，就不自動擷取其內容，改用可取得來源或標示未涵蓋。

### 9.2 最小資料模型

| 紀錄 | 必要內容 |
|---|---|
| Company | 穩定 company_id、證券 market/symbol、名稱、節點類型、題材／環節 |
| Source | source_id、URL、發布者、發布時間、取得時間、定位、審核時間、可用狀態 |
| Relationship | relation_id、起點／終點、類型、產品範圍、來源 IDs、有效期間、審核狀態、版本 |
| Event | event_id、公司、類型、發布／生效時間與時區、資料期間、來源、原公告／更正關聯 |
| FinancialFact | 公司、指標、值、單位、期間起迄、報表口徑、來源、修訂版本 |
| Opinion | opinion_id、creator_id、company_id、market/symbol、content_type、stance、recommendation_kind、條件、摘要、來源定位、發布／取得／審核時間、審核與延續關聯、origin_group_id、版本 |
| Outcome | opinion_id、方法版本、基準與到期日、行情版本、結果／缺失原因、計算時間 |
| Coverage | creator_id、來源、涵蓋起迄、最後成功取得／審核時間、缺漏區間、取得狀態、catalog_version |

Consensus 是由同一版已驗證 Opinion 與 Coverage 衍生的讀取結果，不建立另一份人工維護的真實來源；結果包含 method_version、catalog_version、window_start、cutoff_at、各類帳號數與證據 IDs。

公司身分與證券代碼分開，使改名、代碼變更、海外關係節點不必重寫歷史。未知公司不拿一個近似名稱硬配；未上市節點無證券代碼也可存在。

第一版不做共用萬用內容引擎。各領域使用簡單、可驗證的結構與必要函式；僅在兩個以上模組實際重複時抽取共用驗證。

### 9.3 發布與儲存

低頻人工資料（產業關係、KOL 初始紀錄）先採 repository 內版本化 JSON，透過審閱與正常發布流程更新；新內容與修訂有穩定 ID，不能覆蓋掉歷史意義。這會讓內容更新綁定發布，是小規模第一版的明確取捨。

高頻事件／財務／成效產物使用現有 GCS 模式下的新獨立前綴，例如 `research-events/v1/` 與 `opinion-outcomes/v1/`，保存不可變內容與其來源版本。先在本機／隔離候選位置驗證讀取，再納入正式發布；不得手動覆寫既有 dashboard、report、prediction 或 quant 最新指標。

讀取時驗證 schema、大小、雜湊、日期與來源版本；失敗時只讓對應新區塊不可用，不拖垮既有市場與個股頁。快取以資料版本為基礎，個人頁仍維持 private/no-store，不可快取進公用頁面。

第一版不用新增管理後台。維護者透過受版控的 JSON 與驗證命令編輯；當每日人工內容更新已頻繁干擾程式發布，再評估專用內容後台。

### 9.4 更新責任與失敗策略

| 項目 | 規劃更新方式 | 失敗／過期處理 |
|---|---|---|
| 產業關係 | 維護者每週檢視新公告；每筆最遲 90 日複核 | 待複核標記，保留歷史來源，不繼續聲稱最新有效 |
| 公司事件／財務 | 每個市場交易日，既有資料產物完成後執行一次有界批次 | 顯示最後成功發布日與未涵蓋公司，不寫空快照蓋掉有效版本 |
| KOL 觀點 | 維護者每日或指定內容日確認新紀錄 | 明示收錄截止日及缺漏區間，不宣稱即時全收錄 |
| 成效觀察 | 完成市場行情驗證後重算到期區間 | 缺價或公司行動不明時標記不可計算 |

匯入需有游標、來源去重、有限重試及失敗紀錄。首次回填使用隔離產物，不能讓歷史日期取代目前發布。具體排程時間在實作開始時根據當前 runner 與來源發布時間核對，沿用既有允許窗口，不預先添加系統排程。

## 10. 後續版本：論點日誌與持股共同曝險

### 10.1 投資論點日誌

輸入：關注公司、核心理由、支持來源、反對證據、失效條件、下次檢視日。

例如使用者寫「關注因為營收成長持續」，系統列出後續月營收及原先條件，由使用者確認是否改變判斷。只有結構化且有資料支持的條件才做自動提示，不讓 AI 自行宣布應買賣。

筆記預設私人、可匯出及刪除，修訂保留時間。這需要新的個人內容儲存與權限測試，故不混入第一版。

### 10.2 持股共同曝險

使用者自行輸入持股或權重，先做產業及題材集中度；再展示已確認共同客戶／供應鏈關係。

清楚區分「這些公司都與某客戶有關」和「多少營收依賴該客戶」。缺乏公司營收占比時只能列關係，不能推成投資組合的量化曝險百分比。

不連券商、不讀交易帳戶、不執行交易；跨幣別權重需有使用者提供金額或可驗證匯率。等產業關係覆蓋與維護穩定後再做。

## 11. UI、效能與資訊一致性

- 沿用 `DESIGN.md` 的白底、深藍、資料日期與缺值規則；不全面換版，不新增炫光、3D 或不必要動畫。
- 首屏先呈現可以理解的結論與操作，方法、來源與原始欄位放可展開區塊。
- 所有互動可用鍵盤，焦點可見；關係與漲跌不能只用顏色表達。
- 圖旁有同內容列表，無 JavaScript 時仍能看到核心公司關係與來源。
- 外部來源開啟需避免不可信 HTML 注入；服務端抓來源限制已核准網域並驗證重新導向，不能接受任意 URL 變成內網請求。
- 圖形只載入目前題材與所選公司需要的資料；第一版使用 SVG 與原生 DOM，不載入大型圖形引擎。
- 效能驗收於固定測試條件量測：選定公司後已載入資料的切換目標小於 200ms；新增圖表專用 JS gzip 目標不超過 50KB。這些是產品預算，不是已量得結果。
- 390×844 與 1440×900 為必測尺寸；頁面整體不得橫向溢出，比較表可在明確標示的容器內橫向捲動。

## 12. 成本與維護取捨

第一版不採購資料、不開新付費模型、不新增外部服務帳戶。沿用既有雲端資源不代表零增量成本；記錄新增物件數／大小、批次執行時間、來源請求次數與個人頁讀取次數，在候選環境量測後提供估算。

不在每次使用者開頁時叫模型分析或抓影片。公開資料批次處理，事件先限已涵蓋公司及關注範圍，避免一開始全市場掃描。

主要持續成本預計是人工確認關係與 KOL 語意。前兩個實作週記錄每筆確認耗時與每日新增量，再估每週維護工時；目前沒有依據承諾固定費用或完全自動維護。

擴大前先看：來源取得成功率、過期關係比例、待審觀點積壓、每週人工工時。若更新落後，降低收錄範圍並公開覆蓋，不能靠 AI 猜測補齊。

## 13. 開發與交付順序

各交付包有清楚完成條件，但批准後可連續執行，不為形式上的階段反覆要求確認。

| 順序 | 可驗收交付 | 主要相依 | 粗估投入 |
|---|---|---|---|
| 0 | 資料樣本與來源可行性紀錄、當前工作樹基線、契約確認 | 實作批准 | 1～2 人日 |
